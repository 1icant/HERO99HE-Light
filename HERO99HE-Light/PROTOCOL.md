# 协议分析记录

## v0.1.26 顶部灯带取色与原厂彩色模式

自动取色在应用时对当前未乘按键亮度的预览帧取主导色，忽略近黑分组；无亮色时用键盘主色。仍只发一次 `04/06` mode=3 / colorIndex=0，亮度、鲜亮增强由灯带自身配置决定。

彩色霓虹和跑马按已有 USB 抓包恢复 `04/06` 的 mode=2 / mode=5，colorIndex=7。仅这两种模式声明长度为 4，实际保留七字节参数和原校验算法。每次明确应用发送一次，保留本次连接能力检查和写后 60ms 间隔；不调用 `04/22` 同步，不做分区或逐灯写入。按键包预算、Logo 和后台输入不变。

## v0.1.24 独立灯光

顶部灯带仅在点击应用后发送一次 `04/06`。原厂公开 Legacy 侧灯枚举为 Off=0、SteadyMode=3、BreathingMode=4；RGB、亮度和速度保留 7 字节标准设置。首次应用先读 `82/09` 确认本次连接支持；按键下一包至少在灯带写入 60ms 后。没有侧灯同步或周期性软件灯带控制。Logo 继续使用 `04/0B`，普通按键帧仍用 `08/01`；Esc 专项和实验接口已退役。

## v0.1.23 Esc：一次整键着色后排除 Esc

用户确认 `08/02` 红蓝变化包括实体 Esc；单包 `08/01` 已含键号 1 / 2，但只有 F1 按预期变化。不重扫备用号。新对照先发送一次红色 `08/02`，随即在同一发送事务中提交两包 `08/01`，覆盖其余 100 个位置。之后只以约 4 FPS 更新 `08/01`，让 F1 蓝 → 绿 → 蓝，其余 99 键保持蓝，共 12 帧后结束。由此验证 Esc 留色是否跨帧存续；两条命令不是原子更新，不能假定固件无闪烁。只在停止时经确认执行，不设置模式或配色，不发灯带或 Logo 指令。

实机反馈：组合对照仍未得到预期的 Esc / F1 异色，不把该路径加入常规输出。复核已有 `usb.pcapng`：Esc 单键改色的输出为 `06/00`（例如帧 1965，键号 `00 01`，帧 1967 回显），没有捕获到报告 ID 9 的 `08/01`–`08/04` 实时发包。该抓包证明原厂自定义改色路径，不能作为逐键实时 Esc 的依据。不把配置写入用作动画循环。后续需要本机可用的灯珠映射，或原厂确实能让 Esc 与其他键独立实时变化时的 USB 报文。

## v0.1.22 Esc：两条实时路径

原厂 Legacy 的 `updateFullKeysRGB` 用 `encode(8,2,[r,g,b])`，不经过逐键地址。固定 Report 9 / 63 字节：`08 02 00 01 00 03 R G B`，零填充，尾部仍是补和校验。用户的 `82/0F` 只回空包，尚无本机支持证据。仅允许显式执行 2.5 秒对照（先红后蓝，各五帧，每 250 ms 一帧）；确认 Esc 和 F1 都变色后，才开放本次连接的整键同色常亮 / 呼吸（不超过 20 FPS）。不与 `08/01`、灯带、Logo 或原厂配色写入交织。

另可只写 `08/01` 的地址 1 / 2，各用一种颜色，中途交换。每帧只有一包，不发 101/113 键背景，用于区分多包/大帧问题与物理 Esc 不响应逐键实时寻址。没有观察结果不改默认映射。

## v0.1.19 空确认包等待修正

v0.1.18 的确定缺陷：`82/0F` 首个合法全零数据区会立即报错，中止等待，无法接收可能随后到来的真正数据。用户本次只反馈错误文字，尚未取得原始报文，不能据此确认固件确实会发第二包。

修正为：合法单包零长度、全零数据区仅记为 empty-reply，不占用分包 0，继续原 2 秒窗口，不重发。非零长度 1–17 的特性短响应也保留后继续等；不从声明范围外的填充区读取支持标志。完整特性按有效区解析，长度 0 但固定区非空沿用原厂特性兼容规则。显式声明完整长度的全零数据是有效的 false 能力，与零长度空包区分。校验错误、非法分包等仍立即拒绝。

截止后仅有空/短特性响应，返回 available=false、各能力字段 null、waitExpired=true 和有界原始捕获（最多8包及总计数），不认定不支持。Esc 可继续读取 A1/00 映射；同步可继续读取 84/22 状态，均只读。没有特性写入能力时绝不发 08/04 或 04/22，也不启动该实验模式。正常键盘、04/06 灯带和 Logo 路径不依赖这个查询，不受影响。A1/00 和 84/22 的零长度空包也等待真实数据；超时仍失败，不猜值。

## v0.1.18 Esc 灯珠表与原厂侧灯同步

从官方公开 `CvyBDz8W.js` 核对 Legacy 服务。`82/0F` 设备特性按原厂读取固定数据区；data[9] bit2 是灯珠表、bit3 与 bit4 同时置位才是 RGB565 灯珠控制，data[17] 非零为原厂侧灯同步。缺失、全空、校验异常不假定支持。

`A1/00` 只读查询 Esc/F1 两个键号（`00 01 00 02`）；响应记录 `[idHi,idLo,count,坐标...]`，坐标低 3 位是行、高 5 位是列。重组带序号的合法分包，拒绝回显、未知键号、重复或截断记录。仅在本次连接报告 RGB565 且 Esc 和 F1 均有映射、不重叠时，手动确认使用 `08/04` 测试：`[RGB565高字节,低字节,数量,坐标...]`，单色每 250ms 一次、约 3 秒，仅发送 Esc 对应坐标，不改变日常 08/01 键位。旧 08/01 Esc/F1/95 的 101 键帧、113 槽帧分别与原厂纯构包逐字节一致，这只排除漏编码，不能证明固件将地址 1 映射到实体灯。

已知 `82/09` 样本报告 23 个侧灯、矩阵灯箱尺寸 0 × 0，不能由此推导 `29/03` 可写。新增 `84/22` 读取原厂侧灯同步状态、`04/22` 设置同步开关。只有用户确认、侧灯能力与设备特性明确时才走此路径；先读原值，必要时开启并回读。同步期间不写 `04/06`，继续发送正常按键帧。停止/正常断开尽力还原本次更改；拔线或强退无法保证。回读只是开关状态，不证明 23 灯珠可独立寻址，也不证明原厂同步跟随实时 `08/01` 或能左右异色。

Logo 新增从当前按键 RGB 帧选主导色（亮度加权、忽略近黑）；不乘按键亮度，保留 Logo 的 0–4 档。同色去重，最快约 300ms 发送一个既有 `04/0B` 包，原总发送预算不变。不恢复旧连续灯效。

## v0.1.16 单灯珠 Logo 调度优化（历史）

用户确认Logo是一个灯珠，颜色/亮度正确但响应慢；K槽位2/13/14/43/70/95正确，1/71/97完全无响应，Esc映射不改。新增Logo模式follow-color读取面板主色，keyflash按事件产生160ms主色/黑色，无空间平均或原生新模式，仍04/0B mode3/colorIndex0/speed2/brightness0..4。

Logo最快目标50→25ms。移除每个键盘帧将Logo标脏和同色无条件刷新，仅真实RGB/档位变化或首次启动写；顶部灯带保留原兼容刷新。按键事件唤醒Logo等待，不改变sender包预算；本地延迟工厂在完整按键分包及5ms间隔之后读取最新状态，只发送一次，不排队补发历史帧。事件签名在取样时记录，不能吞掉USB在途期间的新事件。

仍每完整键盘帧最多一个原生尾包，总80pps/至少5ms间隔/8ms排空不变。互动/主色变化优先，侧灯等待达150ms后优先，避免连击饿死侧灯。两路连续变化仍共享剩余带宽，无提升包率或降低按键颜色数。单独快速Logo跳过整键盘渲染/构包；同色去重也释放灯带时隙。

同组8时机纯模拟旧余辉平均73.5ms/最大114ms，新版余辉与keyflash为42.375ms/64ms；稳定主色5秒101按键帧、99侧灯、1Logo。不是固件响应或硬件长期稳定保证。

## v0.1.13 Esc 复核与 Logo 只读查询

2026-11-10 只读复核官方公开 `C2Xbz_H5.js` 与 `B6KProv3.js`：键码字典的 `0x1` 为 ESC / browserCode Escape / USB usage 0x29；实时模块直接编码 numeric keyValue。当前 LED 地址 1 与此一致，没有依据改成 0 或空余号 71/97。输入键码不是 LED 地址，修复后台输入不能证明物理 Esc 灯响应；本版仅新增是否收到过 Esc 的诊断布尔值，不记录输入明细。

官方 `CvyBDz8W.js` 中 Legacy 类型表为主灯 1→起点 1、侧灯 2→6、Logo 3→11。`getEffect(type)` 使用命令 132（0x84）和上述起点，Logo 设置查询因此是只读 `84/0B`：

```text
84 0B 00 01 00 00 [零填充至61] checksum
```

只在本连接能力明确 `logoLight=true` 且停止输出时发送一次；遵循 Report 9 / 63 字节、单包、有效长度 7–56、正确校验与原有发送间隔。响应前 7 字节解释为 mode/colorIndex/R/G/B/brightness/speed，仅作证据展示，不把读取值视作可安全写入的范围。短包、长度超限或校验错误会拒绝，原始捕获附入诊断。未发送 `04/0B` 设置或任何保存/复位指令。

既有真实能力样本 `data[19]=15` 按原厂布尔语义声明 Logo 支持，但不能证明就是 PgDn 下方灯，诊断固定 `physicalLocationVerified=false`。未启用 Logo 控制或其他未知灯位写入。

后台按键使用独立 Windows Raw Input 辅助进程，不改变 HID 灯光接口或输出报文。明确手动开启且互动输出运行才启动；只接受 HERO VID/PID 的扫描码，停止/非互动/退出释放注册。三色编辑与变长时间线也只改变纯 RGB 采样，不提高包数或速率。

## v0.1.12 取色联动与软件增益

新增 6 种 frame-linked 灯带取色方式，仍只构造原有 04/06 mode=3、colorIndex=0 的整条 RGB 报文。主色模式用 RGB 32 级分桶的亮度加权占优组，忽略近黑（峰值小于 8）组；没有亮组时回退平均色。横向采样与左右交融用布局键帽中心，不用硬件 ID 的数字顺序猜位置。键盘画面变化时只跟随完整帧，静态键盘时动态包络可用空闲时隙。

`strip.gain` 为 1–2 的软件增益，旧配置缺失时补 1。最终 RGB 统一乘 `min(gain, 255 / max(1,R,G,B))` 后取整，限制最亮通道并保留色相、黑色；不提高原生亮度字段 0–4，不改变速度字段 2。每帧只应用一次。RGB 已满值纯白无法增亮，不能据此宣称达到原厂最大亮度。

本次重新只读查看官方公开 CvyBDz8W.js，Legacy setEffect 仍按 `[id,colorIndex,R,G,B,brightness,speed]` 传入原有编码路径；未执行官方应用或尝试未知亮度档位。网页顶部 PrtSc 与底部 Fn 显示按新图修正，硬件地址仍为原物理槽位 95/72，数据格式与旧项目键号不变。

| 3 | 当前帧的分包总数 |
| 4 | 当前包序号，从 0 开始 |
| 5 | 本包有效数据长度，最大 56 |
| 6–61 | 数据块，不足补零 |
| 62 | `(0xFF - (0x09 + sum(payload[0:62]))) & 0xFF` |

先将同 RGB 的键按颜色分组。每个颜色段是 `[R, G, B, 键数, keyId...]`；一个段最多 52 个键。把所有段连接为字节流，再每 56 字节切包。**颜色段可以跨 HID 分包边界**，不能把每包当作独立颜色段解析。

软件串行发送一帧的全部包后才计算下一帧，不堆积并发帧；停止/断开会取消后续待发包。实时输出路径不会发送原生模式切换、写入配置或固件更新指令；v0.1.6 的独立氛围灯手动操作见末节。

## v0.1.1 稳定输出策略

原始构包逻辑不变。针对用户反馈“低复杂度效果正常，多色效果乱闪”，在编码器外增加保守的软件输出预算；这些数值是本工具的策略，不是已经确认的固件规格或厂商限制。

- 先原样构包；不超过 4 包的帧不修改 RGB。超过 4 包时，使用确定性的加权中位切分合并到最多 24 色，精确保留原有黑色，再交给同一编码器；如仍超预算则拒绝发送。
- 每个报告完成后至少等待 5ms；完整或中止的帧后至少等待 8ms。帧起始间隔不小于 `max(1000 / FPS上限, 包数 × 1000 / 80)` 毫秒。
- 每次等待完成后才采样最新画面，不并发帧、不追赶积压、不自动重试失败报告；同一连接停止再启动仍保留间隔。
- 处理只用于预览和硬件输出，项目中的原始颜色不被改写。用户已反馈 v0.1.1 颜色正常；后续布局补丁仍需复测。

## v0.1.6 查询专用固定数据区和原厂氛围灯

新报告的 63 字节原始能力响应已单独保存到 `tests/fixtures/hero99he-capabilities.json`，不包含设备标识或其他个人诊断。其 payload[5] 为 0，但 payload[6..61] 非空。原厂 `XPe.checkLightingSupported()` 绕过通用 `decode()`，直接执行 `u.slice(lengthIndex + 1, u.length - 1)`，即读取固定 56 字节数据区。v0.1.5 仅参考通用解包器的结论不完整。

本工具仍严格要求 Report 9、63 字节、`82/09`、单包、正确校验和、声明长度不超过 56；仅在声明长度 0 且固定区非空时按该官方专用规则解析。全零空包仍为未知，非零短长度继续保留缺失字段语义。诊断同时保存 declaredLength、parsedLength、payloadFormat 与原始字节。

真实样本 data[18]=31、data[19]=15 按原厂布尔语义均为支持；不推断为模式位图。data[20]=23 是固件报告侧灯数量；data[21..24] 为零，不启用矩阵灯箱。隔离运行原厂纯解析器得到同一结果，未访问硬件。固件报告数量不是对物理灯珠的独立核实。

原厂服务 `setEffect(2, ...)` 生成 `encode(4,6,[mode,colorIndex,R,G,B,brightness,speed])`。本工具只允许 mode=3、colorIndex=0，brightness/speed 为 0–4 整数。63 字节结构为：

```text
04 06 00 01 00 07 03 00 R G B brightness speed [零填充至61] checksum
```

界面亮度 1–5 档减 1 后传入；它不是灯珠数量。此报文没有灯珠数或逐灯地址，不把顶部灯带当作 5 颗、23 个按键或矩阵输出。以颜色 (0,160,255)、亮度 2、速度 2 比较原厂纯构包结果，63 字节逐字节一致。

只接受本次连接查询确认 sideLight=true、停止实时输出、独立明确许可后的手动命令。Worker 串行发送一次，等待匹配 Report 9 / 04/06 的合法校验回执，2 秒超时、不重试，完成后保留 8ms 间隔。停止会取消等待并等待清理；已发送的效果不能撤销。ACK 不证明物理位置、全灯覆盖或视觉效果，也不保证固件不会自行保存。没有实现 save/reset/恢复/固件命令，需恢复时使用原厂设置。

用户最新反馈颜色控制正常、灯带应不止 5 个。本版澄清亮度档位和固件数量，不据此假定实际灯珠已全部覆盖；不改动已正常的 RGB 编码、后台与保活路径。

## v0.1.7 软件灯效与串行联动

用户随后确认“5个”是网页亮度档位误解，要求扩展键盘灯效、灯带效果、联动和配色。本版未改变 `08/01` 分组、分包、4 包稳帧或能力读取协议。

新增键盘效果均为本地纯 RGB 计算后交给原编码器；配色为 2–8 个 RGB 的循环插值。旧配置缺少配色时由主色/底色补入；缺少 strip 时默认 off。配置只保存模式和参数，不保存许可。

灯带动态只复用 `04/06`、mode=3、colorIndex=0 的已核对报文，以低频常量颜色更新模拟整条动态；不调用未核对的原厂动态模式、不猜逐灯地址。follow 取实际稳帧后键盘颜色的算术平均 RGB；react 使用与键盘余辉相同的页面输入事件及时间。所有模式的速度由主速度控制，follow 的亮度来自已缩放键盘帧，其余只乘一次主亮度，再由原厂独立亮度档位控制。

Worker 只在开始时接受本次会话的独立许可和本次连接查询 sideLight=true。原生更新在整帧键盘发送完成后等待共用 sender.ready；单个控制包也经 sender.sendControl 记录 5ms 包间隔、8ms 排空及 80 包/秒预算，双方不并发。每次合法 ACK 完成后至少 250ms 才能再更新，不变颜色去重、不补发积压。联动 ACK 超时 350ms，全流程错误停止双方、不自动重试；普通只读查询和单次手动纯色仍为 2 秒。

停止/撤销许可/拔出取消等待并等待已开始发送的操作清理；不发送关闭、保存或恢复指令。固件是否自行记忆这些原生设置及长期影响未知，界面保留单独许可与提示。新增模式的软硬件组合需要实机反馈；软件时钟验证不能替代视觉同步、实际帧率或不同固件验证。

## v0.1.8 组合帧兼容策略与发送/回执分离

用户反馈原生灯带单独配置可工作，一旦配置按键颜色后失效。确定的代码问题是运行状态禁用应用、许可只在 start 时锁存；没有在实机证明固件内部覆盖机制。对此采用保守兼容组合，而非猜测新协议：完整 `08/01` 按键帧 → 共用发送器排空 → 一次 `04/06` 常量色 → 至少 250ms 后才允许下一组合。不改 RGB 编码/键号/原厂模式 ID，不增加未经确认的逐灯地址。组合会将键盘动画降为最多约 4Hz，设备排空后实际更低；仅按键仍沿用原预算/FPS与250ms保活。

组合内即使灯带颜色相同，也在每个键盘帧之后重新提交；旧版永久去重不再用于组合场景。独立灯带允许 keyboard=false，只写原生常量颜色，静态重复去重。activeStrip 为启动快照，页面编辑先暂存，点击应用再更新；跟随模式仍读取实时键盘设置/画笔/平均色。

流式 native 包与实时 RGB 同样按 `sendReport` 的 Promise 完成确认已交给 USB，不阻塞等待每包 ACK。被动监听只计数 Report 9、63 字节、`04/06`、单包、合法校验和回执，停止/断开移除监听；不记录其他输入。缺 ACK 不是不支持，也不是已应用，不关联 ACK 与单个颜色、不自动重试失败报文；USB 失败停止整个流。原有只读能力查询和保留的单次低层设置接口仍严格等待对应响应，均不放松格式/校验约束。

主页面统一应用事务：停止并等待旧流排空 → 有明确灯带许可且缺少本次能力时查询 → 用新配置启动（恢复原先是否输出按键）。取消 token 防止停止/断开/撤销许可/导入后迟到的查询或请求自动重启。连接本身不查询、不发送。数据不上传，诊断分开记录提交量、观察到的 ACK 数与 hardwareApplied=null，避免把主机完成当成硬件视觉验证。

这是针对用户症状的兼容实现，非固件行为证明；仍需实物复测顶部灯带与按键输出是否真正同时持续生效。设备自行记忆、重复原生设置的长时影响及恢复行为也未得到验证。

## v0.1.9 移除全局节流与帧尾调度

v0.1.8 的 250ms 组合等待会限制所有键盘帧，属于本工具策略问题，不是已知固件要求。本版移除全局等待，保留未变化键盘帧 250ms 保活；不改 RGB 编码、键号、最多 4 个按键包和原厂命令。

灯带以 50ms / 20Hz 为最快目标。动态按键帧基准速率为 `1000/frameInterval(fps,keyPackets)`，预留其 90% 包预算；灯带目标速率为 `min(20, 80-keyPackets*keyRate*0.9)`。例如四包、目标 20FPS 时目标周期 125ms；完整帧边界和 USB 耗时可使实际更慢。未变化按键画面仅预留保活带宽；独立灯带不预留键盘带宽。50ms 是软件目标，不是协议最小间隔声明。

灯带到期且有键盘帧要发时，`sendFrame` 先顺序发送全部 `08/01` 分包，再按 5ms 间隔追加一个 `04/06` mode=3 尾包，并按 keyPackets+1 计算同一发送事务的 80 包/秒预算与 8ms 排空。没有键盘帧时仍走同一 sender 的 sendControl；不另开并发 HID 写入。计划周期从采样/帧起始计算，避免尾包偏移误将 50ms 更新降成隔帧更新；实际原生发送间隔随键盘包数/USB 时间变化，所有包仍受发送器节流。

按键写入使灯带变脏，到期后即使颜色不变仍兼容刷新；独立纯色去重。不等待流式 ACK，错误停止且不重试。诊断增加实际 USB 原生提交耗时峰值，不能当作设备视觉耗时。32 个键盘效果仅为本地 RGB 计算，30 组色卡不变。未新增原厂效果 ID、矩阵/逐灯写入、保存/复位或固件命令；高频原生设置的长期影响仍需实机确认。

## v0.1.10 灯带优先刷新、独立亮度与显式操作

取消 90% 按键带宽预留，灯带目标周期为 25ms（最高目标 40Hz）。将 sender 的按键周期 nextFrameAt 与共用包预算 nextBudgetAt 分离：按键等待二者；原生控制只等待预算/包间隔，不受按键 FPS 周期阻塞。每个完整按键帧尾可追加灯带，keyPackets+nativeTail 的全部包数仍计入总预算；不发送并发数据、不在分包中间插入控制。四包键盘+一包原生的预算周期为 62.5ms，对应约 16Hz；不承诺所有模式 40Hz。单次检查/设置使用原生控制等待路径，仍需排空。

灯带颜色不再乘按键亮度：跟随模式由 caller 提供未乘按键亮度、经相同稳帧处理的颜色帧；其余直接使用灯带自身 RGB 或自身动态包络。原生报文仍固定 mode=3、colorIndex=0、亮度/速度 0–4，网页 5 档对应亮度字段 4。最高 RGB 仍 255，无增压/未知亮度参数；移除软件重复压暗不意味着能突破物理亮度上限。

按用户要求移除两个许可勾选；仅开始/应用按钮事务向后台发送明确启用参数，连接/预览/导入/暂存参数不自动启用。后台仍验证本次能力与显式启动参数，停止取消 token 不变；设备选择仍由浏览器确认。高频原生设置可能记忆的风险未因移除界面勾选而消失，尚无长期硬件验证。
